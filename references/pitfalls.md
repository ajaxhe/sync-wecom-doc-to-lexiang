# 红线与已知限制

> 动 `norm()`、索引逻辑、或任何「改写 ID 字符串」的念头之前，**必读本文**。
> 本文只写**现行规则**，不记录调整历史。

---

## 一、红线（违反即制造重复条目或泄露密钥）

### 🔴 1. 绝不改写待提交的 ID 字符串

剥 `?scode=`、URL ↔ 裸 docid 互转、`file_id` ↔ 分享链接互转 —— 服务端按 `source.href.id`
**字节级严格比对**去重且**不做任何规范化**，改写 = 造出一个**新身份** = **重复条目**。

| 提交形态 | 服务端判定 |
|---|---|
| 与既有条目逐字相同（含 `?scode=`） | 去重（`special`） |
| 剥掉 `?scode=` | **新增**（`add_num`） |
| 裸 docid `w3_…` | **新增**（`add_num`） |

→ 唯一允许的「替换」是**回填既有的原始字符串**（为了触发字节命中），**不是**把字符串规范化后提交。

### 🔴 2. `norm()` 仅供客户端匹配判等，绝不回传给服务端

回传 `norm()` 的值 = 造新身份 = 重复。

`norm()` 规则（**仅供客户端判等**）：去首尾空白 → 剥 `?…` query → **保留** `#page=<pageId>` fragment
（子页身份锚点，剥了会错配）→ 微盘 `s?k=<k>` **保留 `k`** → host 小写（path/id 大小写不改写）。

### 🔴 3. 不覆盖 `profiles/*/config.json`

文件内含**个人 MCP Token**。禁止 `scp` 覆盖、禁止进任何代码/skill 托管平台
（`profiles/.gitignore` 已忽略整目录，仅留自身）。分享 skill 时整体剔除 `profiles/`。

### 🔴 4. 禁止 mock / 占位假数据

直连真实 MCP 端点（**只连乐享侧**）。凭证缺失 / 未填模板时报**明确错误**并 `exit 1`，**不降级 mock**。

### 🔴 5. `create` 返回 `code:0` ≠ 成功

只代表任务已创建，参数校验在执行阶段。**必须**轮询 `import_describe_task`。

### 🔴 6. 目录扫描失败 → 主动中止，不「跳过匹配强行提交」

`entry_list_children` 失败时若继续提交，就失去了唯一能防重复的能力。
脚本设计为打印明确错误并 `exit 1`，**这是有意的**，不要为了「让它跑起来」而加 fallback 空索引。

## 二、成败与失败口径（不可违反）

1. **任务结束判定只看 `data.status`**（describe 回包顶层字段，**不参考任何其他字段**）。官方枚举 5 个值：
   `page_processing`（页面导入进行中 x/n）/ `processing`（正在导入，初始化/解压 zip）→ 进行中，继续轮询；
   `succeed`（成功）/ `failed`（失败）/ `canceled`（已取消）→ 终态，**到终态立即汇总输出**，
   不做「等条目排空」之类的二次等待。轮询预算用尽仍未到终态 → `exit 1` 并提示稍后用 `status` 查询。
2. **失败文档与原因的唯一来源 = `failed_items[]`**（`failed_code` + `failed_reason`，逐条**原文**）。
   `entries[].status` **只用于进度展示，不参与任何判定**——条目级 failed / failed_reason
   不进报告、不当失败数。
   **工程兜底**：脚本在 `_rpc_post` 回包出口用 `strip_entry_errors` 把 `entries[]` 条目内部的
   错误说明字段（`failed_reason` / `failed_code` / `err_message` / `error_detail`）**统一剔除**，
   `failed_items[]` 原样保留；stdout 与 `--debug` 日志拿到的都是**同一份已过滤回包**。因此
   Agent 从任何渠道都看不到条目级错误说明——失败原因只能来自 `failed_items[]`，没有第二条路。
3. **接口判成功即成功、判失败即失败**。不判断文档/文件内容是否为空、不解释「这个失败其实已导入」、
   **不给任何失败码开白名单**（任何「哪些失败其实算成功」的名单都会过期、漏判，且让 `exit code`
   与接口结论不一致）。
4. **部分失败 = 整任务 `failed`**。`failed` ≠ 全军覆没，看 `failed_items[]` 条数 vs `total_num`；
   退出码一律 `exit 1`，无例外。`canceled` 同样 `exit 1`（附「任务已取消」文案，不打印授权提示）。
5. 顶层 `err_message` 是泛化文案（恒为「导入失败，请查看失败文档」），**没有排障价值**；只渲染
   `failed_items[]`。
6. Agent 汇报失败时**照接口原文讲**：不替服务端解释、不建议「换个写法再试」；判断「这条失败影响不影响
   使用」是用户/服务端的事。
7. 若服务端想让某个失败码不算失败，**唯一正确的修改位置是接口侧**（不把它放进 `failed_items[]`），
   不是本 skill。

**判据（想加任何「判断」前先问）**：这条结论是**接口刚刚告诉我的**，还是**我推断的 / 上次观测的**？
是后者 → **不许**写进 skill 与提示词，留在对话层（当次有效，可随时被新回包推翻）。
这条判据同时扛着**免升级设计**（SKILL.md 红线 9）：接口新增文档类型时本 skill 必须不改一行就能导入，
任何按类型分叉的硬编码都会把新类型卡在旧版本上。

## 三、已知限制与行为规则

### 3.1 索引只扫目标目录**一层** → 子页做候选时可能重复

`entry_list_children(parent_id)` 只返回**直接子条目**。而 `include_subpages=true` 时，
智能文档的**子页落在「文档条目之下」（第二层）**，`source.href.id` 形态为
`…/smartpage/a1_xxx#page=<pageId>`，**不在目标目录下**。

**后果**：若直接把**子页 URL（含 `#page=`）**当候选提交，归一索引匹配不到 → 判 `NEW` → **可能重复**。

**规则：不引入递归扫描**（会显著放大请求量与耗时；正常用法是维护「根文档候选」而非逐个子页）。
这是**有意接受的限制**；若确有「只导某个子页」的需求，让主理人先裁决，不要自行加。

### 3.2 微盘：分享链接**原样提交**，不换 `file_id`

| 提交形态 | 服务端 |
|---|---|
| 分享链接（`s?k=…`）**原样**提交 | ✅ 接受，条目 `href.id` = 链接原文 |
| `file_id`（`fi…`） | 兼容（老配置可继续用），但与链接**互不相等** |
| 分享链接**换成** `file_id` | ⚠️ 换了身份，与既有「链接身份」条目对不上号 → 重复 |

- `norm()` 故意**保留 `s?k=` 的 `k`**（它才是分享链接的身份本体），所以链接与 `file_id` 的归一值
  **永不相等**——「拿链接去索引里找 `file_id` 条目」永远找不到。**同一资产只固化一种写法**。
- 候选里填**用户从企微复制到的那条链接原文**即可，不改写、不换算。

### 3.3 `dry-run` 的两个盲区

1. **不校验 ID 合法性**：被判 `add_num` 只表示「服务端认为这是新身份」，不代表能导入成功——
   别只看 dry-run 就交付。
2. **对 `conflict_strategy` 全盲**：见 3.4。

### 3.4 `conflict_strategy`：必须显式下发，绝不依赖服务端默认

| 取值 | 含义 | 风险 |
|---|---|---|
| `skip` | 跳过已存在的 | **安全档**：不动目的端既有条目 |
| `replace` | 覆盖目的端 | ⚠️ **以本次提交为准替换该目录内容，既有条目会被删除** |
| `keep_both` | 两者都保留 | ⚠️ 会产生重复条目 |

- **不传该字段时，服务端默认行为 = `replace` 语义**：「本次提交集合」=「保留下来的集合」，
  不在集合内的既有条目会被删掉，且任务自身报 `succeed`、**全程无任何删除提示**。
  → `replace`（及不传）只能在**专用导入目录**使用。脚本一律显式下发（默认 `skip`）。
- **`dry-run` 对该策略是盲的**（四路 `dry_run_stats` 完全一致）→「dry-run 报零新增」**不能**当作
  「真跑不会动目的端」的依据。
- **`special_num` ≠ 安全**：命中之后是「跳过」还是「覆盖」，由 `conflict_strategy` 决定，
  不由匹配结果决定。
- **回包不携带 `conflict_strategy`** → 事后无法追溯，下发时必须显式指定并打印。
- **去重索引有延迟**：新建条目要过几分钟才进服务端去重索引 → **不要用短间隔的两次 dry-run 差异下结论**。

### 3.5 任务结束判定只看 `data.status`

**规则**：任务是否结束**唯一依据** = describe 回包顶层 `data.status`（官方枚举：
`page_processing` / `processing` = 进行中；`succeed` / `failed` / `canceled` = 终态），
**不参考 `entries[]` 等任何其他字段**。到终态立即汇总输出；轮询预算用尽仍未到终态 →
`exit 1` 并提示稍后用 `status` 查询。

### 3.6 调用路径：先看当前可见 tools 再选路，不要写死

官方规则（MCP resource `lexiang://docs/instructions/v1`）：

> 可见工具清单由 MCP 服务按 **company / feature_flag / allowlist** 动态过滤。
> 可见 tools 包含目标业务工具 → **直调**；不包含但包含 `call_tool` → **必须经它包装**。

- 可见集是**服务端可调状态**（后台开关会改）→ 只有「每次先探 `tools/list`」才能自动适应；
  把路径写死成任一条，开关一动整条链路失效。`mcp_call()` 已按此实现并留兜底，
  **不要**在业务代码里绕过它直连 MCP。
- **「目录里可发现」≠「`tools/list` 里可见」**：前者是注册表，后者是本次下发的可见集；
  服务端开关与本地会话可能不同步（放回 + 重启才刷新）。
- 报 `tool is not allowed: <工具名>` = 服务端本次没下发它，**既非凭证过期、也非配置错**。

### 3.7 诊断守则

1. **判定「平台禁止 X」之前，必须拿到官方原文里的规则句。**「我这边复现了」只能证明当前上下文如此；
   反过来也别把服务端的变化「洗」成自己的环境差异。缺平台方视角时：记录现象、归因标待确认、去问平台方，
   **既不写「平台禁止」，也不写「与平台无关」**。
2. **错误信息必须保真**：服务端在报「工具不允许 / 不存在」时回的是**纯文本，不是 JSON**——
   见到「content 不是合法 JSON」先怀疑这一类，而不是编码 / 网络。不要用笼统的解析失败掩盖真因。
3. **「凭证问题」与「可见性 / 权限问题」一条命令分开：直调 `whoami`。** 成功 = token 有效 →
   「只拒业务工具、包装就通」这种选择性拒绝绝不可能是凭证问题。

## 四、接口侧踩坑备忘

| 坑 | 现象 | 处理 |
|---|---|---|
| `entry_list_children` 参数名 | 传 `entry_id` → `code:51 validation error: parent_id: value is required` | 用 **`parent_id`** |
| 末页仍返回 `next_page_token` | `limit=100` 取回 10 条仍带 token；用该 token 再请求返回**空数组** | 终止条件 = **本页为空**，不是「没有 token」，否则死循环 |
| 手工创建的条目无 `source` | 建索引时读到 `None` | 跳过没有 `source.href.id` 的条目 |
| `failed_items` ≠ `entries` | 失败项**不在** `entries[]` 里 | 两个数组都要渲染（见「二、成败与失败口径」） |
| `dry_run_stats` 计数为 0 时不回字段 | 实测 `add_num=None, special_num=3`；反例 `add_num=2, special_num=None` | `None` **等价 0**，展示前归一 |
| `disk files list` 混着两类资产 | 文档类带 `doc_url`、纯文件类不带；`id` 一律是 `fi…` | 有 `doc_url` 提交 `doc_url`，否则提交 `file_id`；`folder` 跳过 |
| `content_version` 多形态 | `{"mt":…}` / `{"hash":…,"v":…}` / `None` | **只透传，不解析不改写** |
| 企微侧回包 `extra_identity_context` | 回包含内部身份说明 | 输出前剔除，不外泄 |
| stdout 被管道接走时顺序错乱 | stderr 错误文案跑到 stdout 前面 | `sys.stdout.reconfigure(line_buffering=True)` |

## 五、输出样例与实现约束

```text
[profile=default] 预演（dry_run，不写库）
  目标目录   : https://<租户>.lexiangla.com/pages/<target_entry_id>
  候选       : 3 条
  冲突策略   : skip —— 跳过已存在的（安全档：不改动目的端既有条目）
  既有扫描   : entry_list_children → 10 条
WARN: 目标目录存在 2 条同源条目（entry_id: <entry_id_B> (created_at=1789446554), <entry_id_C> (created_at=1789901234)），归一索引取最早一条 <entry_id_B>
  候选提交保真清单（实际提交字符串 · 匹配结果）:
    #1 MATCHED→复用既有       submit=https://doc.weixin.qq.com/doc/w3_AE8…?scode=<scode>
    #2 MATCHED→复用既有       submit=https://doc.weixin.qq.com/smartpage/a1_AC0…?scode=<scode>
    #3 MATCHED→复用既有       submit=fi…
        └ <候选 key（文档名称），填了才打>
  将新增 : 0 条（add_num）   已存在 : 3 条（special_num）
  task_id    : <task_id>
  状态       : page_processing   进度 None/3
  状态       : succeed   进度 3/3
  服务端统计 : dry_run_stats add_num=0, special_num=3

  ── 同步结果预演（dry-run，未写库）──          # 真跑时是「── 同步结果 ──」
  任务       : <task_id>   succeed   3/3
  ✅ 新增 : 0 条（无）
  ♻️ 已存在·复用 : 3 条                        # 带目端条目名 + 两端链接
    1. <目端条目名>
       源端 https://doc.weixin.qq.com/doc/w3_AE8…?scode=<scode>
       目端 https://<租户>.lexiangla.com/pages/<entry_id>
    2. …
  ❌ 失败 : 0 条（无）
  接口计数   : add_num=0  special_num=3        # 与本地匹配数交叉校验，不等则打 ⚠️ 口径不符
```

> ⚠️ 样例里的「既有扫描 → 10 条」是**时点快照**，不是稳定判据——目的端条目会被编辑删除，
> **不要把任何一次输出的条目数当断言用**（这也是 SKILL.md 要求 Agent 不要盘点目的端的原因）。

**同源重复条目的索引规则**：目的端真实存在「同一资产两种写法」的重复条目（归一后键相同）。
索引构建遇到键冲突时**取 `created_at` 最早的一条**（稳定、可预测：只要最早那条还在，
索引值就不变，重复跑结果一致），并打印 WARN 行（见样例）。

**三条实现约束（改 `scripts/sync.py` 时必须保持）**

1. `create` 必须逐条打印**实际提交的字符串**与匹配结果（保真自证）——
   便于核对「输出字符串与既有条目逐字一致、无被剥离/改写」。
2. **脚本不得对形态做任何「能不能导入」的判断** —— 不拦、不拒收、不预判、不因「形态不认识」而中止；
   候选一律原样提交，把接口回包（含 `failed_items[]`）原样返回给 Agent。
3. `render_report` 的每一档都必须能**对回**接口字段或既有扫描（新增/已存在 → `dry_run_stats` + 归一匹配；
   失败 → `failed_items[]`；条目名/链接 → `entry_list_children`）。**禁止**自造判断档（如「内容有更新」）——
   接口没有该维度，硬造出来的档会误导客户（见 `import-api.md`「⭐ 报告能取到什么」）。
